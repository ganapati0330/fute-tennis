# フテ猫のテニス対決 🎾

スマホ2台を**QRコードでつないで**対戦できる、ブラウザテニスゲームです。
サーバーを一切使わず、**HTML1ファイル**だけで動きます。小学校低学年〜向け。

👉 **あそぶ:** https://ganapati0330.github.io/fute-tennis/

登場キャラクター：**フテ猫**・**クロネコさん**・**チャッピーちゃん**

## あそびかた

| モード | ないよう |
|---|---|
| 📱📱 2台で対戦 | QRコードで2台のスマホを直接つないで対戦 |
| 📱 1台で二人対戦 | 1台の画面を上下に分けて、2人で対戦 |
| 🤖 CPU対戦 | クロネコさんと対戦（よわい / ふつう / つよい） |

- **うごかす**：画面を指でなぞった分だけキャラクターが移動します（相対ドラッグなので指の下に隠れません）。
  **左右だけでなく前後にも動けます**——ネットに詰めたり、後ろに下がったり
- **ボレー**：ネット近くで、バウンドする前に打つと「ボレー！」。通常より鋭い球になります
- **サーブ**：タップするとボールが**高くトスされ**、頂点でラケットが当たります
  - サーバーは**ベースラインの後ろ**から打ちます（前には出られません）
  - **立ち位置は自由に選べます**。画面をスライドすると黄色いバーの上を左右に移動でき、
    センターマークより内側には入れません。選んだ位置は次のサーブにも引き継がれます
    （タップ＝サーブ、スライド＝移動、で区別しています）
  - 1ポイント目はデュースサイド（自分から見て右）、以降は1ポイントごとに左右交代
  - ボールは**斜め前のサービスボックス**（黄色く光る四角）に入れます。外れると「フォルト」
  - **ジャストミートするとフォルト率が激減**します（実測：普通の打点16.7%に対して0%、
    カーブをかけた場合は32.9%に対して0%）
  - **サーブはワンバウンドさせてから返します**。ノーバウンドでのボレーリターンは反則です
- **球種の打ち分け**：**打つ瞬間に自分がどう走っているか**で5種類に変わります
  | 走りかた | 球種 | 弾道 |
  |---|---|---|
  | 大きく踏み込む ⬆️⬆️ | **スマッシュ** | 最速・最も低い |
  | 前に踏み込む ⬆️ | **はやい球** | 速く・低く・深い |
  | それ以外 | ふつう | ラリーが進むほど深く |

  **ロブとドロップは走り方では出ません**（意図的な指示のみ）。深い球を追えば必ず後ろに下がるため、
  これをロブ要求と解釈すると実プレイの8〜9割がロブ／ドロップになってしまいます（実測値）。
  | 指示 | 球種 |
  |---|---|
  | **画面を2回タップ** | **ドロップ** |
  | **後ろへフリック** | **ロブ** |

  ドロップは「少し下がる」でも出ますが、狙って出すのは難しいので**ダブルタップ**でも指定できます。
  タップから1.4秒間「ドロップ ねらい！」の状態が続くので、ボールに走りながらでも間に合います。

  使い分けのコツ：相手がネットに近ければ**ロブ**で頭を越し、相手が下がっていれば**ドロップ**で前に走らせます。
  CPUも同じ判断で球種を混ぜてきます（頻度は難易度に比例）。
  PCは矢印キーで4方向、1台対戦の2Pは I / J / K / L キー。
- **回転をかける**：打つ瞬間に指を**すばやく弾く（フリック）**と回転がかかります。**サーブも同様**で、
  2回目のタップのときに弾くと曲がるサーブになります
  | フリック方向 | 回転 | 効果 |
  |---|---|---|
  | ◀ 左に弾く | **カーブ** | 飛行中に左へ曲がる |
  | ▶ 右に弾く | **シュート** | 飛行中に右へ曲がる |
  | ⬆️ 前に弾く | **ドライブ** | 順回転。大きく浮いて急降下する |

  「走る＝球種」「弾く＝回転」は独立しているので、**同時にかけられます**
  （例：踏み込みながら右に弾く → スマッシュ＋シュート）
- **止まって打つと狙いが正確に**：走りながら打つと球種は選べますが**狙いがぶれます**。
  止まって構えると足元に黄色い輪と「**ねらい ◎**」が出て、コートに入りやすくなります。
  ただし**必ず入るわけではなく**、ラケットの端で捉えれば止まっていても外れます
  | 打点 | 止まって | 走りながら |
  |---|---|---|
  | ほぼ芯 | 100% | 100% |
  | やや外し（55px） | 100% | 61% |
  | 大きく外し（95px） | 47% | 2% |
- **スマッシュ**：相手が高いロブを上げてきたら、落ちてくる間に**赤い輪**が出ます。
  ボールが輪に入って「スマッシュ！」と出た瞬間にタップすると、通常の約1/3の滞空時間で飛ぶ
  強烈なスマッシュに。早すぎても遅すぎても普通の球になります。
  ボールが打点圏にある間は自動の打ち返しが止まるので、狙う時間があります（約0.26秒）
- **落下点マーカー**：コートに出る点線の輪がボールの落下点です。白ならイン、赤ならアウト。
  先回りして待ち構えましょう
- **スコアボード**：自分側の画面下に `15 - 30` 形式で常時表示（左が自分）。
  ポイントごとにコート中央にも大きく出ます
  - 40-40は「**デュース**」。以降は**2ポイント連取**でゲーム。1ポイントリードは「**アド**」表示で、
    取り返されるとデュースに戻ります
- **音声実況**：審判がテニスの読み方でコールします
  `0=ラブ / 15=フィフティーン / 30=サーティ / 40=フォーティ`
  サーバーの点数を先に読むので、30対0なら「**サーティ ラブ**」、同点なら「フィフティーン**オール**」、
  40対40は「デュース」。ほかに「アウト！」「ネット！」「ツーバウンド」「ゲーム、フテ猫」
  「ゲームセット。フテ猫のかち！」もコールします。
  タイトル画面と試合中の 🗣 ボタンでON/OFFできます
- **サーブ**：1ゲームの間は同じ人が打ち続け、ゲームが終わると交代します（スコアボードの🎾が目印）
  - ただし**1ゲームずつ取り合った最終ゲーム（ファイナル）**は、片方だけがサーブすると有利になるため、
    **1本 → 2本ずつ**の順で交代します（テニスのタイブレークと同じ方式）。
    スコアボードに「ファイナル・サービス交代」と表示され、交代時は審判もコールします
- **BGM**：画面に応じて2曲を切り替えます（いずれも継ぎ目のないループ）
  | 場面 | 曲 |
  |---|---|
  | タイトル・設定・接続・あそびかた・決着後 | **白いラインへ** |
  | 試合中 | **白い線の上** |

  切り替えは0.35秒のクロスフェードです。🔊 ボタンでON/OFF。
  実況中は少しだけ音量を絞り、読み上げが終わると戻ります

### 音が出ないときは

1. iPhone横の **マナーモード（消音スイッチ）** をOFFにする（オレンジが見えない側）
2. 本体の**音量**を上げる
3. タイトル画面の「**🔈 音のテスト**」を押す
   - 「OK おとは ながれています」→ 端末側の設定の問題です
   - 「NG」→ 表示される `code: ...` の行を控えてください。原因が特定できます
- **ボール**：たかく弧をえがいて飛び、コートで**ワンバウンド**します（影の位置が落下点）
  - 白いラインの**外に落ちたらアウト**（打った人のまけ）
  - **2回バウンド**したら、打ち返せなかった人のまけ
  - ラケットの**まんなか**で打つとまっすぐ、**はし**で打つと大きく横に曲がります。
    曲げすぎるとアウトになるので、ねらいどころが勝負の分かれ目です
- **とくてん**：テニスとおなじ `0 → 15 → 30 → 40 → ゲーム`
  （40-40 はデュース表示になり、次の1点をとったほうがゲームをとります）
- さきに **2ゲーム** とったほうの勝ち
- 決着後は「**もういちど**」（同じ相手で再戦）と「**メニューへ**」（タイトルへ戻ってモード選択）を選べます
- キーボード（PC）：`←` `→` で移動、`Space` でサーブ。1台対戦の2P側は `Z` `C`

## 2台でつなぐ手順

1. 2台とも **おなじ Wi-Fi** につなぐ
2. 1台目で「**親機になる**」（フテ猫）、2台目で「**子機になる**」（クロネコさん）を選ぶ
3. 親機に出た **QRコードを、子機のカメラで読み取る**
4. 子機に出た **QRコードを、親機のカメラで読み取る**
5. つながると自動で試合がはじまります

> **カメラが使えないときは**
> 各画面の「コードをコピー」を押して、LINEやメール、AirDropなどで相手に送り、
> 「ここにコードをはりつけてもOK」の欄に貼って「はりつけたコードでつなぐ」を押してください。

### つながらないとき

- 2台が**別のWi-Fi**（片方が4G/5G）になっていないか確認してください
- 学校や公共のWi-Fiは、**プライバシーセパレータ**（端末間通信の遮断）が有効なことがあり、
  その場合は仕組み上つなげません。「1台で二人対戦」であそんでください
- 一度もどって、もう一度①からやり直すと直ることがあります

## 技術メモ

- **単一HTMLファイル**（約374KB）。外部CDN・外部サーバーへの通信は一切なし
- 通信は **WebRTC DataChannel**。シグナリングサーバーの代わりに、
  SDPを必要最小限（ice-ufrag / ice-pwd / fingerprint / 接続候補）まで圧縮した
  **250文字前後のコード**を作り、QRコードで手渡しします
  → QRが小さく収まり、スマホでも一発で読み取れます
- **STUN**（Google公開サーバー）で各端末の公開アドレスも取得し、LAN内アドレスと一緒に
  コードへ載せています。これにより**別ネットワーク同士でも接続できる場合があります**
  （対称NAT・多くのモバイル回線では不可。確実に繋ぐにはTURN中継サーバーが必要で有料）
- ICE収集は「LAN内と公開アドレスが1つずつ揃った時点」で早期に打ち切ります（上限4.2秒）
- ブラウザがLANアドレスを隠すために使う36文字のmDNS UUID（`xxxxxxxx-....local`）は、
  16バイトに戻してbase64urlで詰め直し、1候補あたり14文字節約。IPv6候補は長すぎるので除外
- QRは **canvas** に整数ピクセルで描画（Safariは width/height を持たないインラインSVGを
  潰してしまい、コードが文字のまま表示される不具合があったため）。
  誤り訂正レベルMと規格どおりの4モジュールのクワイエットゾーンを確保
- ホスト権威モデル。子機は自分のラケットをローカル予測で動かし、
  ボールは速度から外挿（dead reckoning）するので、通信間隔（30Hz）による遅延を感じません
- 子機の画面は180°回転させ、**どちらの端末でも自分が手前**に見えます
  （文字・キャラクターは逆回転して常に正立）
- コート上の位置はワールド座標のままで問題ありませんが、**高さから導かれるもの**
  （ボールと影の距離、振り上げたラケット、頭上に浮くラベル、跳ね上がる体、火花の落下方向）は
  「この画面でどちらが上か」を知る必要があります。`UP()` / `FLIP()` / `airY()` を通して
  一元的に変換しており、同じワールド状態を親機・子機でレンダリングして
  180°回して重なることをテストで確認しています
- キャラクター画像は WebP + base64 で埋め込み（16ポーズ）
- ボールは高さ `z` をもつ擬似3D。重力・反発係数つきで落下し、影の大きさと濃さ、
  ボールの描画位置と大きさで高さを表現。画面端での反射はなく、**着地点でイン/アウトを判定**
- ゲームカウントは本式のアドバンテージ方式（`gameState()` が deuce / adv / won を判定）
- サーブ時の入力はタップとドラッグを区別（移動量26px・700ms以内をタップと判定）。
  これが無いと、位置を変えようと画面に触れた瞬間にサーブが飛んでしまいます
- 画面外へ完全に出たボールの保険処理は、**すでにワンバウンドしているか**で裁定を分けます。
  速い深いサーブは1バウンド後に世界の外へ抜けてから2バウンド目を迎えることがあり、
  一律に「アウト」にすると**サービスエースが失点になっていました**
- ボールの高さは**厳密な放物線**で積分しています（`z += vz·dt − ½g·dt²`）。
  素朴なオイラー積分では狙いより約7px先に落ち、サービスライン際を狙った球が
  幻のフォルトになっていました。着地判定も、ステップ終端ではなく
  **実際に地面と交わった時刻を解いて**その位置で行います
- カーブをかけたサーブは、曲がる分を見越して狙いをボックス内側へ補正します（補正量は打点の質に比例）
- サーブは「トス → 任意のタイミングで打撃」の2段階。**打点の高さ `z` から接触品質 `q` を求め**、
  球速（`900 + 560q`）・着地の深さ・狙いの誤差をすべて `q` で決めています。ジャストミートは
  `q > 0.82`。CPUは難易度ごとに打点のばらつきを変えて同じ計算式を通ります。
  2ndサーブだけは打点が悪くても着地点をボックス内にクランプするので、ダブルフォルトは起きません
- トス中はサーバーの位置が固定され、サービスサイドはポイント数の偶奇で自動的に左右交代。
  着地判定はコート全体ではなくサービスボックスに対して行い、外れれば「フォルト」
- 奥側のプレイヤーが高くトスすると、ボールはベースラインより上に描かれます（テレビ中継と同じで、
  これ自体は正しい投影）。その位置にはスコアボードがあるため、**ボールが板の帯に入っている間だけ
  板の側を薄く**して、どちらも隠れないようにしています。
  「タップ！」の表示も画面外に出そうなときは輪の横に回り込みます
- コートは上下に余白を取ってスコアボード用の帯を確保。これが無いと、ベースライン後方に立つ
  サーバーが自分のスコアボードの裏に隠れてしまいます
- プレイヤーは自陣内を2次元に移動。打球は「相手コートのどこに落とすか」を先に決め、
  距離と球速から飛行時間 `T` を逆算して初速を求めるので、**ネット際からのボレーは自動的に
  低く速い弾道**、ベースラインからのロブは高い弾道になります
- 入力は「走る」と「弾く」を分離して読み取ります。フリックの判定は速度そのものではなく
  **直近100msの速度が、その前の200msの速度からどれだけ跳ね上がったか**（バースト量）。
  こうしないと、コートを素早く横断するドラッグが全部カーブ扱いになってしまいます
- 横回転は「加速度」ではなく「**横にずれるピクセル数**」で指定し、飛行時間から加速度を逆算します。
  ロブはスマッシュの2倍以上滞空するため、同じ加速度では曲がり幅が4倍以上変わってしまうためです。
  同じフリックでどの球種も同じだけ曲がることをテストで検証しています
- 「止まると正確」は3つの効果の合成：①芯を外したときの散りが小さくなる
  ②カーブ量を見越して着地点をライン内側に引き戻す ③ランダムな散らばりが小さくなる。
  ただし③には下限（12%）を残してあるので、完全な保証にはなりません
- 順回転（ドライブ）は**そのボールだけ重力を1.85倍**にして表現。着地点は `launch()` が解き直すので
  狙いは変わらず、弾道だけが高く・急降下に変わります。バウンドすると回転は減衰します
- キャラクターは**テニスモーションシート**から切り出した48枚のスプライトで描画
  （2キャラ × 前面/背面 × 12ポーズ：構え・サーブ①②③・フォア①②③・バック①②③・
  スライディング・決めポーズ）。連結成分の自動検出で切り出し、元絵の地面の影は除去しています
  - **手前のプレイヤーは背面図、奥は正面図**で描きます。テニス中継と同じ見え方で、
    子機は画面が180°回転しているため自動的に入れ替わります
  - フォア／バックはボールの左右で自動選択。背を向けているか正面かで左右が反転することも
    考慮しています
  - 大きく伸ばして（打点圏の60%以上）かつ走りながら追いついた打球は**スライディング**に
    なります（実測でおよそ20球に1回）
  - シートはポーズごとに描画サイズが違う（構えと決めポーズが大きく、寝そべるスライディングは
    小さく見える）ため、**ポーズ別の倍率表**で見た目の大きさを揃えています
  - 手描きのラケット・振り抜き軌跡・スクワッシュ＆ストレッチの処理はすべて不要になり、
    描画コードが大幅に簡素化されました
- 共通部分は「頭部が描く大きな楕円」＋「手が描く小さな楕円」＋「手首の遅れ角」の3要素。
  テイクバックでヘッドが大きく遅れ、腕が加速してもしばらく置き去りになり、
  最後に一気に追い越す——この**タメと解放**がスイングらしさの正体です。
  振り抜きの軌跡には残光（スウッシュ）を重ね、奥側に回ったフレームはキャラクターより先に描画。
  楕円の半径は体の幅より大きく取ってあるので、ラケットが体に重なりません
- 打球の 0.25 秒前（到達時間から逆算）に自動でテイクバックを開始するので、接点でちょうど振り抜けます
- 音声実況は **Web Speech API**（`speechSynthesis`、ja-JP）。2台対戦では親機が読み上げ文を
  データチャネル経由で子機にも送るので、両方の端末で同じコールが流れます。
  実況中はBGMを自動で絞ります（ダッキング）
- 効果音は **Web Audio API**（`AudioBufferSourceNode`）で再生。`<audio>` 要素を使い回す方式は
  `pause()` → `currentTime` → `play()` の競合で `AbortError` が起き、連打すると音が欠けるため。
  Web Audio なら1音ごとに独立したボイスが立つので、ラリー中の連続ヒットでも取りこぼしません
  （`AudioContext` が使えない環境では従来の `<audio>` プールに自動フォールバック）
- 打球音は球種ごとに別音源：**hit**（強打）/ **soft**（ロブ）/ **volley**（ボレー）/ **bounce**（バウンド）。
  球威に応じて音量も変化します
- BGMは MP3（96kbps ステレオ）を base64 で埋め込み。試合曲 約426KB（波形相関 0.964）、
  メニュー曲 約297KB（同 0.948）。128kbpsでも相関はほぼ変わらないため96kbpsを採用
- 2曲はそれぞれ独立したゲインノードを持ち、切り替え時に**0.35秒のクロスフェード**を行います。
  メニュー曲のデコードに失敗した場合は試合曲で代替します
- **BGMも効果音と同じ Web Audio で再生**します（`decodeAudioData` + `loop` 付き
  `AudioBufferSourceNode`）。`<audio>` 要素＋巨大な data URI は端末によっては読み込みに失敗し、
  効果音だけ鳴ってBGMが鳴らない状態になります。副次的に、**ループの継ぎ目が無くなり**、
  音量をゲインノードで制御できるようになりました（iOSでは `<audio>.volume` が読み取り専用のため重要）。
  `<audio>` の `play()` が必ず失敗する状態でも再生されることを検証済み。
  デコード自体に失敗した場合は `<audio>` 経路と合成ループへ二段階でフォールバックします
- 効果音11種と**予備のBGMループ**は、読み込み時に **JavaScriptで波形を合成**して WAV 化。
  `blob:` URLは file:// 由来のページでSafariが読み込めないことがあるため **data: URI** で埋め込み、
  ジェスチャが来る前に同期的に生成・`load()` 済みにしてある
  （音声ファイルを同梱しないためファイルサイズを節約）
- BGMは自己修復する設計。監視タイマーが1.5秒ごとに「停止していないか」に加えて
  **再生位置が進んでいるか**を確認します（iOSでは音声合成がオーディオセッションを奪い、
  再生中のまま時計が止まることがあるため）。止まっていれば再生し直し、
  ダッキングが解除されずに音量が下がったままの状態も検出して戻します
- 実況のダッキングは `onend` / `onerror` で即座に解除し、さらに安全タイマーでも解除します。
  読み上げは次のポイントで `cancel()` されるため `onend` が発火しないことがあり、
  これが無いと音量が下がったまま戻りません
- 自己診断 API（`SND.selfTest()`）で、再生位置が実際に進んでいるかを測定して結果を画面に表示
- iOS対策：`<audio>` 要素をロード時に無音WAVで先行生成し、
  ジェスチャハンドラ内で**同期的に** `play()` を呼んでアンロック。
  `body` は `position:fixed` でスクロールバウンスを抑止

### バランス検証（`tests/balance.js`）

キャラクターを自動操作するボットを3段階（初心者 / 標準 / 上級）用意し、
CPU3段階と総当たりで各160ポイントを自動プレイして統計を取ります。
測定するのは平均ラリー数・1ポイントの長さ・1試合の長さ・勝率、そして
**「誰がアウトを打ったか」の内訳**です。

この検証で、狙いのブレ判定が絶対速度基準だったために
人間側（最高速1180）だけが常に「走っている」と判定され、
CPU（最高速400〜760）はほぼ常に「足が止まっている」扱いになる
という構造的な不公平が見つかりました。アウトの内訳は人間87対CPU28。
自分の最高速に対する割合で判定するよう修正し、45対57まで対等になっています。

同じ検証で、コート幅1000に対して移動速度が速すぎると
全球に追いつけてしまい最長2160往復・43分のラリーが発生することも判明したため、
移動速度の引き下げと「18往復を超えると徐々に狙いが乱れる」疲労を導入しました。

調整後の勝率（各160ポイント）:

| ボット \ CPU | よわい | ふつう | つよい |
|---|---|---|---|
| 初心者 | 0.75 | 0.07 | 0.00 |
| 標準 | 0.73 | 0.30 | 0.00 |
| 上級 | 0.92 | 1.00 | 0.08 |

平均ラリー3〜11往復、1試合83〜180秒。

## 2台でつなぐ

**サーバーは一切使いません。** 接続情報（WebRTCのSDP）を150文字程度に圧縮し、
QRコード・リンク・テキストのいずれかで手渡しします。

### 招待リンク方式（おすすめ）

1. 親機が「🔗 リンクを おくる」→ LINEなどで送信
2. 子機はリンクを**タップするだけ**で参加画面が開き、返信リンクが出る
3. 返信リンクを親機に送り返し、**親機が画面を開いたまま**タップすると接続完了

リンクは `#j=`（招待）と `#a=`（返信）で区別し、読み込んだ直後にアドレスバーから消します。
返信は `hashchange` で受け取るため、親機のページを開いたまま操作する必要があります
（開き直すと接続の片側が失われるため）。新しいページで返信リンクを開いた場合は、
その旨を表示してタイトル画面に戻ります。

### QRコード方式

近くにいる場合はカメラで読み取り合うのが最速です。コードのコピー＆ペーストも可能です。

### 同じWi-Fiでなくても繋がります

接続コードには**LANアドレスとSTUNで取得した公開アドレスの両方**を載せています。
別回線どうしでもリンクを送り合えば接続できます。ただし**対称型NAT**
（携帯キャリア回線や一部の組織ネットワーク）の場合はTURN中継サーバーが必要になり、
現在の構成では繋がりません。その場合は「1台で二人対戦」をご利用ください。

### 2台対戦の位置ずれ（修正済み）

サーブ準備の位置固定処理を**両方の端末が自分の判断で実行**していたのが原因でした。

- 子機は `doServe()` を呼ばない（親機に `t` を送るだけ）ため `tossPX`（トス時の立ち位置）が
  未設定の 0 のままで、トス中に自分のキャラが左端へ歩き出していました
- さらに子機は、同期で受け取っているだけの親機キャラにも位置固定をかけていたため、
  パケット間で動いては次の同期で戻る、という 30Hz のチラつきが出ていました

`ownsPaddle()` を追加し、**自分が動かす権利のあるキャラだけ**に固定処理を適用するようにしました。
`tossPX` も、どちらの端末でもトス開始時に自分で latch する方式に変更しています。
実機2台を WebRTC でつないだ E2E で、トス中の左右のブレが親機・子機とも 0px であることを確認しています。
